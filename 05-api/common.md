# 공통 API 계약 초안

- 상태: 검토 대기 — 담당자 확인 전

## 경로·권한·입출력

- 제안 기본 경로는 `/api/v1`이다. 아래 표의 경로는 이 접두사를 생략한다.
- JSON 요청·응답을 사용한다. 본문이 있는 요청은 `Content-Type: application/json`을 사용한다.
- 권한 `R`은 USER/ADMIN 모두 가능한 서비스 조회, `U`는 일반 사용자, `A`는 관리자다. 이번 초안은 모든 업무 API에 사용자 문맥 헤더를 요구한다. 비로그인 공개 접근은 별도 확정 전 제공 계약에 포함하지 않는다.
- 사용자는 헤더로 선택하고 서버에 등록된 사용자 정보에서 역할·멤버십을 조회한다. 세부 권고안은 [시연용 사용자 헤더](#시연용-사용자-헤더--사용자-요청을-반영한-권고안)를 따른다. 개인 API 본문으로 `userId`, `actorId`, `createdBy`, 지급 수량·점수 확정값을 받지 않는다.
- 관리자도 다른 사용자의 알림을 대신 읽음 처리할 수 없으며, 관리자 이벤트 응모는 금지한다.
- `{eventId}` 등 경로 ID는 필수 UUID 문자열이다.
- DTO 필드명은 camelCase. `?`는 nullable, 요청 표의 `선택`은 생략 가능이다. 나머지 응답 필드는 항상 반환한다. 목록에 값이 없으면 `[]`이다.
- `int`는 JSON 정수, `long`은 JSON 64비트 정수, `decimal`은 정밀도를 보존하는 십진 문자열 제안이다. JS 소비자는 `long`의 정밀도 범위를 구현 시 함께 확인한다.
- `instant`는 UTC `Z`로 응답한다. 요청은 `Z` 또는 명시적인 오프셋을 요구한다. 시간대 없는 문자열을 받지 않는다.
- `date`는 KST 업무 날짜 `YYYY-MM-DD`, `month`는 KST 업무월 `YYYY-MM`이다.
- 운영 시각 입력 예: `2026-09-28T18:00:00+09:00` → 응답 `2026-09-28T09:00:00Z`. 일일·월간 초기화는 KST 자정이다.
- 시각 판정이 필요한 응답에는 `serverTime`을 포함한다. 카운트다운·응모 가능 여부는 서버가 반환한 시각과 상태로 판단한다.
- 이미지 쓰기 필드는 `imageKey`, 읽기는 화면용 `imageUrl`로 제안한다. 업로드·키 검증·URL 생성 방식은 담당 기능 계약에서 정한다.

## 응답 봉투 — 현행 코드

```json
{
  "success": true,
  "code": "SUCCESS",
  "message": "성공했습니다.",
  "data": { "id": "0199abcd-1234-7000-8000-000000000001" }
}
```

```json
{
  "success": false,
  "code": "COMMON-002",
  "message": "요청 값이 올바르지 않습니다.",
  "data": null
}
```

이하 응답 타입은 `data` 내부다. 실패에는 실제 4xx·5xx를 사용하고 `data=null`을 유지한다. 빈 성공은 HTTP 200과 `data=null`로 제안하며, 봉투를 HTTP 204에 실어 보내지 않는다. 새 리소스 생성은 201, 완료된 동일 요청 재조회는 200을 기본으로 제안한다.

## 목록 조회

| 형식 | 요청 쿼리 제안 | 응답 `data` — 현행 모델 필드 |
| --- | --- | --- |
| `Page<T>` | `page` 기본 1, `size` 기본 20·범위 1~100 | `items:T[]`, `page:int`, `size:int`, `totalElements:long` |
| `Cursor<T>` | 최초 `cursor` 생략, 이후 `nextCursor` 사용; `size` 기본 20·범위 1~100 | `items:T[]`, `nextCursor:string?`, `totalElements:long` |

페이지는 **1부터** 시작한다. 크기 기본값·상한은 이 문서의 제안이며 core 모델이 정한 값은 아니다. `totalPages`, `hasNext`는 이 계약의 응답 필드가 아니다. 기본 정렬은 별도 기재가 없으면 `createdAt DESC, id DESC`; 커서는 동일 정렬을 고정하고 불투명 문자열로 전달한다. 기간 필터 `from`, `to`는 선택 `instant`이며 `[from,to)`를 적용한다. 표의 조회 필터는 별도 필수 표시가 없으면 모두 선택이다.

## 중복 요청

| 작업 | 제안 식별 기준 | 같은 요청 재처리 |
| --- | --- | --- |
| 응모 | `Idempotency-Key` 헤더, 1~100자; 사용자·이벤트·키 | 접수 성공 건은 기존 영수증을 200으로 반환하고, 저장된 거절 건은 최초와 같은 4xx·오류 코드를 반환한다. 추가 차감하지 않음 |
| 미션 제출 | 같은 헤더; 사용자·미션·키 | 저장된 제출 결과 재사용; 새로운 퀴즈 답변은 새 키 |
| 출석 | 사용자·KST 출석일 | 같은 날 기록·보상 재사용. 자정 이후의 요청은 새 업무일 요청 |
| 게임 결과 | 서버 발급 `playId` | 최초 확정 결과 재사용; 처리 중이면 202 |
| 당첨 취소·재추첨 | 취소 대상 `drawResultId` + 실행 키 | 취소 1건에 연결된 재추첨 1건 재사용 |
| 이벤트 취소·제외·회수 | 원본 차감/지급 및 검토 결정 ID | 실제 반환·회수 결과 중복 반영 방지 |
| 읽음 처리 | 사용자·알림 ID 또는 본인의 미읽음 집합 | 이미 읽음이면 성공 유지 |

응모·미션에서 같은 키로 다른 본문을 보내면 409 `IDEMPOTENCY_CONFLICT`를 제안한다. 이 오류 코드는 제안이다. 같은 키의 재시도는 현재 시각이 마감 후여도 기존 확정 결과를 반환한다. 응모 거절 재시도는 처음 거절한 4xx 상태·오류 코드를 다시 반환하며 성공 봉투나 `EntryReceipt`로 바꾸지 않는다. 저장된 거절 기록은 E05/E06에서 조회한다. 키만 저장하는 것과 원본 입력의 동일성 확인은 별도이므로 제출 답변 등과 대조해야 한다. 관리자 생성 요청에 공통 멱등 응답을 약속하지 않는다.

## 오류

| HTTP | 코드 | 상태 |
| --- | --- | --- |
| 400 | `COMMON-002` 입력 조건 위반 / `COMMON-005` JSON·UUID·타입 해석 실패 | 현행 코드 |
| 500 | `COMMON-001` | 현행 코드 |
| 404·405·406·415 등 | `HTTP-{상태}` | 현재 MVC 표준 예외 처리 |
| 401 | `USER_CONTEXT_REQUIRED`, `USER_CONTEXT_INVALID` | 제안, 시연용 사용자 헤더 누락·미등록 사용자 |
| 409 | `USER_MEMBERSHIP_MISMATCH` | 제안, 선택 멤버십 헤더와 DB 정보 불일치 |
| 403 | `ACCESS_DENIED`, `ENTRY_MEMBERSHIP_NOT_MET`, `ADMIN_ENTRY_FORBIDDEN` | 제안 |
| 404 | `RESOURCE_NOT_FOUND` | 제안, 업무 리소스 없음·소유권 은닉 정책은 구현 협의 |
| 409 | `STATE_CONFLICT`, `IDEMPOTENCY_CONFLICT`, `ALREADY_ENTERED`, `TICKET_LIMIT_EXCEEDED`, `INSUFFICIENT_TICKETS`, `EVENT_NOT_OPEN`, `MISSION_NOT_OPEN` | 제안 |
| 429 | `RATE_LIMIT_EXCEEDED`와 `Retry-After` | 제안, 응모·출석·미션 제출·게임 결과 제출에 적용 |

최종 업무 오류 번호·공개 메시지는 담당자가 정의한다. 아래 API의 오류 열은 공통 400·인증·권한·404·500 외의 주요 분기다. 빈도 제한 수치는 담당자 운영값이며 기능 적용 자체는 확정이다. 탐지 수치, 내부 어뷰징 근거, 예외 원문을 사용자 오류에 넣지 않는다.

## 시연용 사용자 헤더 — 사용자 요청을 반영한 권고안

2026-09-28 사용자 답변에 따라 별도 로그인 API 대신 헤더로 가상 사용자를 선택하는 방식을 명세한다. 최소 계약은 `X-User-ID` 하나이며, 요청한 멤버십 헤더는 DB 값 확인용 선택 항목으로 권고한다.

| 헤더 | 필수 | 형식·처리 |
| --- | --- | --- |
| `X-User-ID` | 모든 업무 API | 등록된 사용자 UUID. 서버가 `users`를 조회하여 사용자 문맥 생성 |
| `X-User-Membership` | 선택 | `excellent`, `vip`, `vvip`. 전달하면 DB 멤버십과 일치해야 함. 생략하면 DB 값 사용 |
| `Idempotency-Key` | 각 API 표에 지정한 작업 | 사용자 선택과 무관한 요청 중복 식별 키 |

```http
POST /api/v1/events/0199abcd-1234-7000-8000-000000000010/entries
Content-Type: application/json
X-User-ID: 0199abcd-1234-7000-8000-000000000001
X-User-Membership: vip
Idempotency-Key: entry-0199abcd-1234-7000-8000-000000000099

{"ticketCount":2}
```

- 멤버십 헤더로 DB 멤버십을 변경하거나 등급을 상향하지 않는다. 등급을 바꿔 시연할 때는 해당 등급의 사전 등록 사용자를 선택한다.
- `X-User-Role`은 받지 않는다. 관리자 API는 `users.role=ADMIN`만 허용한다. `X-User-ID`로 선택한 사용자를 생성자·검토자·처리자로 기록한다.
- 필수 ID 누락은 401, UUID·멤버십 형식 오류는 400, 미등록 ID는 401, 등급 불일치는 409, 역할 불일치는 403으로 제안한다. U01 역시 이 헤더를 사용한다.
- 이것은 **시연용 사용자 문맥 전달이며 신원 인증이 아니다**. 임의 ID를 보낼 수 있는 호출자는 다른 사용자나 관리자를 선택할 수 있다. 개발·통제된 시연 환경에 한정하고, 외부 공개 운영에서는 검증된 인증 또는 신뢰할 수 있는 진입 계층이 사용자 문맥을 생성해야 한다. 브라우저가 보낸 헤더를 그대로 운영 권한으로 신뢰하지 않는다.
- 헤더 검증 오류도 [응답 봉투](#응답-봉투--현행-코드)로 반환한다. 프론트엔드가 다른 origin이면 CORS 허용 헤더에 위 항목을 반영한다.
- `INACTIVE` 사용자 처리와 테스트 사용자 목록·시드 제공 방식은 사용자 문맥 세부 계약의 후속 확인 항목이다. 사용자 선택 목록 API를 현재 요구사항에 없는 전체 개인정보 조회로 확대하지 않는다.
