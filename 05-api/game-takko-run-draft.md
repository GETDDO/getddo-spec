# 타꼬런 연동 계약

- 상태: **2026-10-16 사용자 채택 — A안·120Hz·xorshift32·FE 요청 형식으로 정렬**. 최초 초안은 게임 프론트 담당 박소연 작성. 이후 사용자가 BE를 초안에 맞추도록 요청하고, 활성10분 정상 종료·서버 경과시간 검증 후속을 각각 선택했다. 명세 채택과 코드·FE·테스트·배포 완료는 구분한다.
- 확정된 기준: [최소 보상 점수 400점](../02-domain/game.md#보상-지급), [서버 판정 원칙](../02-domain/game.md#결과-판정).
- 공통 흐름: G03 시작 → 플레이 → G04 일괄 제출. 플레이 ID·토큰·재시도·결과 응답·보상·오류 은닉은 [색깔 게임 연동 계약](game-color-word-draft.md)의 2·5·6절과 같은 방식을 따른다. 이 문서는 타꼬런에서 달라지는 부분만 적는다.

## 2. 현재 프론트 규칙 (2026-10-16 기준)

크롬 공룡 달리기처럼 점프로 장애물을 피하며 달린다. 장애물에 한 번 닿으면 끝난다(목숨 없음).

- 점수 = `floor(달린 거리 / 10)`. 거리는 매 순간의 속도 × 시간을 더한 값이다.
- 스테이지는 점수로 정한다. 스테이지마다 속도와 나오는 장애물이 다르다.

| 스테이지 | 시작 점수 | 목표 속도(px/s) | 높은 장애물 | 두 개짜리 확률 |
| ---: | ---: | ---: | --- | ---: |
| 1 | 0 | 420 | 없음 | 0 |
| 2 | 400 | 540 | 있음 | 0 |
| 3 | 1,000 | 660 | 있음 | 0.25 |
| 4 | 1,800 | 800 | 있음 | 0.4 |

- 스테이지가 바뀌면 속도가 한 번에 바뀌지 않고 목표 속도로 서서히 따라붙는다(초당 남은 차이의 5배).
- 장애물 종류·다음 장애물 간격·두 개짜리 여부를 난수로 정한다.
- 점프는 누른 시간에 따라 높이가 달라지고(일찍 떼면 낮게), 착지 직전 0.12초 안에 누른 점프는 착지하자마자 뛴다.
- 일시정지·탭 이동 시 자동 정지, 재개 카운트다운이 있다.

400점은 스테이지 2 시작점과 같다(ADR-020 배경과 일치).

## 3. 검증 방식 — A안 채택

### A안 (채택): 같은 판을 서버에서 다시 돌려 보기

색깔 게임과 같은 원칙이다. 서버가 같은 장애물·같은 점프 입력으로 판을 다시 돌려, 어디서 부딪혔는지와 점수를 직접 계산한다.

필요한 것:

- **seed:** G03의 `gameData.seed`. 장애물 생성에 색깔 게임과 같은 xorshift32를 쓴다.
- **고정 간격 진행:** 지금 프론트는 화면 프레임마다 다른 시간 간격으로 진행해, 같은 입력이어도 기기마다 점수가 조금씩 달라진다. 정확히 1/120초 고정 간격(tick)으로 진행하도록 프론트를 바꾸고, 서버도 같은 간격으로 계산한다. 반올림한 8.333ms를 반복해 더하지 않는다.
- **점프 입력 기록:** 몇 번째 tick에 누르고 뗐는지.
- **판정 자료:** 장애물 그림 크기표, 캐릭터·장애물 충돌 영역 값. 규칙 버전에 묶어 서버와 공유한다.

G03 `data` 예시(색깔 게임 공통 필드 생략):

```json
{
  "ruleVersion": "takko-run-v1",
  "rules": { "minimumRewardScore": 400, "maxTicks": 72000 },
  "gameData": {
    "generatorVersion": "takko-run-generator-v1",
    "seed": 123456789,
    "tickMs": 8.333333333333334
  }
}
```

G02의 rules도 위 두 공개 필드를 사용한다. maxTicks는 사용자 선택으로 기존 초안에 보완한 활성10분 상한이다. tickMs는 1000/120의 수치이며 실제 물리는 dt=1/120으로 계산한다. 색깔 게임의 gameData에는 tickMs를 추가하지 않는다.

G04 요청 예시:

```json
{
  "playToken": "example-opaque-token",
  "validationData": {
    "endTick": 5421,
    "inputs": [
      { "tick": 0, "type": "press" },
      { "tick": 14, "type": "release" },
      { "tick": 302, "type": "press" },
      { "tick": 330, "type": "release" }
    ]
  }
}
```

위 값은 형식 예시다. 예시 seed로 실제 계산한 값이 아니며, 공통 테스트 예제는 구현 시 고정한다.

| 필드 | 의미 |
| --- | --- |
| `endTick` | 0부터 시작하는 마지막으로 진행한 tick 번호. 충돌 또는 시간 종료 번호이며 실행 횟수는 endTick+1이다 |
| `inputs[].tick` | 달리기 시작 후 실제로 달린 tick 번호(일시정지·카운트다운 제외). 오름차순 |
| `inputs[].type` | `press`(누름) / `release`(뗌). 소문자 문자열만 사용 |

서버 판정:

1. 매 판 G03 성공 후 대기하고 첫 점프를 tick0 press로 기록해 달리기 시작한다. 저장한 seed·규칙으로 tick0부터 endTick까지 양 끝을 포함해 진행한다. 같은 tick의 입력은 배열 순서대로 적용한 뒤 물리를 한 번 진행한다.
2. `endTick`에서 처음 충돌하거나, 충돌 없이 `endTick=71999`에 도달해야 자연 종료다. 활성10분은 총72,000회 진행이다. 이전 충돌·충돌 후 추가 기록·10분 이전 임의 이탈은 무효이며 FE도 같은 종료 경계에 멈춘다.
3. 점수는 서버 계산값을 쓴다. 400점 이상이면 보상 자격이 생긴다.
4. G03→G04 서버 경과시간과 활성시간 대조는 이번에는 적용하지 않는다. 허용 오차·거절 기준은 색깔 게임과 동일하게 후속 계약으로 남긴다. 판정 가능한 입력·크기·종료 상한만 검사하며 새 부정 차단 기준을 임의 추가하지 않는다.

한계: 색깔 게임과 같다. seed가 공개되므로 프로그램이 완벽한 입력을 미리 계산할 수 있다. 기록만으로 사람이 했는지는 증명하지 못한다.

### B안 (미채택, 대안 기록): 시간 상한만 확인

프론트는 지금처럼 점수와 함께 실제로 달린 시간(`activeMs`)과 점프 횟수만 보낸다. 서버는 그 시간 동안 낼 수 있는 최대 점수를 계산해, 제출 점수가 그보다 크면 거절한다.

- 장점: 프론트·서버 작업이 적다.
- 단점: 점수를 서버가 계산하지 않는다. 시간 안에서 점수를 부풀리는 건 막지 못해 "사용자 제출 점수를 그대로 인정하지 않는다"는 원칙과 맞지 않는다.

## 4. 프론트 변경 사항 (A안 기준)

- 화면 프레임 대신 고정 tick으로 진행(화면은 tick 사이를 보간해 그린다).
- `Math.random` 대신 G03 seed의 xorshift32로 장애물 생성. 장애물 생성 외에 같은 난수를 쓰지 않는다(효과음·흔들림 등은 별도 난수).
- 점프 누름·뗌을 tick 번호로 기록해 종료 시 한 번에 제출.
- 같은 seed·입력이면 Java와 TypeScript의 결과(종료 tick·점수)가 같은지 공통 예제로 확인.

## 5. 시간·입력 한도·동일 입력

- endTick은 Java int로 표현 가능한 정수다. 의미상 범위는0~71999이며 입력 tick은0~endTick 비감소 순서다. 첫 입력은 tick0 press다. 범위·순서·시작·종료 위반은 INVALID이며 상한 밖 요청은 물리 재생 전에 거절한다.
- G04 본문 최대1MiB(1,048,576바이트), inputs 최대10,000개다. 둘 중 하나라도 초과하면413 GAME-008로 거절하고 결과를 확정하지 않는다. 필드 누락·문자열 숫자·정수 범위 초과·소수·미지원 type·색깔 answers 혼합은400 COMMON-005다.
- totalTicks/action/PRESS/RELEASE는 이전 미게시 BE안의 형식으로 이번 계약에 포함하지 않는다. endTick/type과 섞어 보내지 않는다.
- 일시정지·탭 이동·시작/재개 카운트다운에는 활성 tick을 증가시키지 않는다. 정지 때 키를 놓은 효과는 다음 활성 tick의 release로 보존하고 재개 입력보다 앞선 실제 배열 순서를 유지한다. pause/resume 자체는 보내지 않는다.
- G03 규칙·seed·생성 버전은 해당 판에 고정한다. 규칙이나 그림이 바뀌어도 발급한 판을 새로운 물리로 소급 판정하지 않는다.
- 입력 동일성은 endTick·입력 배열의 tick/type 순서로 비교한다. JSON 키 순서·공백은 영향이 없지만 같은 tick의 입력 순서를 바꾸면 다른 기록이다. 색깔 게임의 기존 입력 해시는 바꾸지 않는다.
- 권한·결과 응답·404/409/202·분당10회 제한·429 Retry-After·재시도·KST 완료일·통계·일일1장 보상은 기존 채택된 공통 게임 계약을 유지한다. ADMIN은 시작 체험만 가능하며 결과·통계·보상은 활성 USER만 처리한다.

## 6. 판정 데이터와 계산 순서

- 고정 원본: FE b43acc220c53cd931a143e6c2c7bf265e696098a의 takkoRun.ts, takkoRunAtlas.ts, takkoRunStageAtlas.ts 물리·충돌 데이터다. 가변 dt와 Math.random만 이 계약의 고정120Hz·xorshift32로 바꾼다. 원본 확인은 코드 대조이며 실제 FE 수정 완료를 의미하지 않는다.
- xorshift32는 색깔 게임과 같은 state ^= state << 13, state ^= state >>> 17, state ^= state << 5의 32비트 연산 뒤 unsigned(state)/2^32로 변환한다. seed는 기존 범위1~4294967295다.
- 난수는 첫 장애물 추출 → 이중 장애물 여부(확률0인 단계도 소비) → 필요한 경우 두 번째 추출 → 다음 간격 추출 순서로 소비한다.
- 매 tick은 입력 적용 → 점수 기준 단계·속도 추종 → 거리 → 점프 예약/수직 이동/착지 → 장애물 이동·제거 → 필요 시 생성 → 충돌 판정 순서다.
- 기존 폭840·캐릭터x96/크기88·충돌 좌우22/발8·중력2800·점프1000·키해제420·예약0.12초를 유지한다. 장애물은 atlas41개 ×0.5, 원본 스테이지 풀과 순서, 1단계 높이90 이하·두 번째 높이80 이하·간격46, 장애물 좌우20%/상단10% 축소 기준을 고정한다.
- 처음 생성 거리는504, 생성x860, 다음 생성 거리는 현재거리+현재속도×(0.65+random×0.7)+180이다. dt=1/120, 속도 추종은 (목표속도-현재속도)×min(1,5×dt)다. 고정 데이터 변경 시 기존 발급 판 지원과 새 버전 계약을 함께 검토한다.

## 7. 선택 이력·후속

- 변경 전: FE 초안과 BE의 미게시 60Hz·LCG·TAKKORUN·totalTicks/action 안이 달랐다.
- 변경 후: 사용자의 “내가 맞추자 전부 맞춰줘” 요청으로 FE의 A안·TAKKO_RUN·120Hz·xorshift32·endTick/type을 채택했다. 추가 질문에서 활성10분 정상종료 및 서버 경과시간 대조 후속을 각각 선택했다.
- 명세 반영과 실제 FE 변경·Java/TS 교차 검증·개발 DB 설정·배포 완료는 별도다. 이 변경으로 타이밍·주문의 규칙/보상이나 다른 게임을 확정하지 않는다.
- 과거60Hz·LCG 구현의 전체2257개 테스트 성공은 이 계약의 성공 기록이 아니다. 새 계약의 테스트 및 공통 입력·점수 예제 대조가 필요하다.
