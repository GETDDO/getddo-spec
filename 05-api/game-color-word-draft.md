# 글자색깔 맞추기 연동 계약

- 상태: 2026-10-12 사용자 채택. 명세 우선 및 제안 방식 사용 지시에 따라 아래 색깔 게임 계약을 구현 기준으로 사용한다.
- 대상: GD-153 설계, GD-156 시작, GD-157 검증, GD-159 결과, GD-160 보상, GD-166 프론트 연동.
- 확정된 플레이 규칙: [게임 도메인](../02-domain/game.md#글자색깔-맞추기-규칙).
- 공통 API 외형: [게임 API](game.md), [공통 계약](common.md).
- 적용 범위: 색깔 게임의 코드·규칙 버전·G03/G04 전송·시간 판정·중도 종료·보상일·재시도 계약. 마지막 절의 운영 한도·타 담당 연동 후속은 별도 관리한다.
- 파일명은 기존 초안 링크 호환을 위해 유지한다. 사용자 채택과 실제 프론트 반영·통합 검증 완료는 구분한다.

## 목표와 역할

현재 프론트는 자체 난수로 문제를 만들고 종료 시 최종 점수만 제출한다. 이를 서버가 같은 문제와 입력 기록으로 점수를 다시 계산하는 흐름으로 바꾼다.

| 담당 | 할 일 |
| --- | --- |
| 백엔드 전민규 | 플레이 발급, 문제 생성 기준 보존, 답변 기록 검증·점수 판정, 통계·보상 자격 처리 |
| 게임 프론트 담당 | 서버 발급 정보로 문제 생성, 답변·시간 기록, 종료 제출·재시도, 서버 결과 표시 |
| 응모권 윤태형 | 기존 지급 서비스로 등급 응모권 발급·이력·만료 처리 |
| 어뷰징 석종수와 전민규 | 판정 근거·빈도 제한·확인된 차단 기준의 연동 |

시작 요청 1회와 종료 제출 1회로 연결한다. 문제마다 HTTP 요청하지 않는다.

## 1. 게임 식별과 규칙 버전

- 게임 목록의 `id`는 DB UUID, `code`는 프론트 플레이어 선택용으로 구분한다. 색깔 게임 코드는 `COLOR_WORD`다.
- 프론트의 임시 `game-color` ID 기반 플레이어·안내 콘텐츠 선택을 `code` 기준으로 연결한다.
- 서버가 시작 시 적용한 규칙 버전과 문제 생성 기준을 보존한다. 종료 시 최신 규칙으로 바꾸어 계산하지 않는다.
- 시작 응답의 `rules`는 그 플레이에 적용할 공개 규칙이다. 색깔 게임의 G03 DTO에 추가하며, 게임별 시작 정보는 `gameData`에 둔다. 초기 규칙 버전은 `color-word-v1`, 생성 버전은 `color-word-generator-v1`이다.

## 2. 시작 — G03

`POST /api/v1/games/{gameId}/plays`

공통 `X-User-ID`를 사용하며 본문은 없다. 실제 게임의 시작 버튼에서 호출하고 응답을 받은 후 카운트다운과 플레이를 시작한다. 실패 시 플레이를 시작하지 않는다. 화면 진입이나 안내창 열기만으로 호출하지 않는다.

### 시작 계정 자격 — 2026-10-14 사용자 선택

- 변경 전: G03의 일반 사용자 권한 표기로 인해 관리자 시작을 차단하는 구현안을 검토했다.
- 변경 후: 색깔 게임 시작은 DB 상태가 `ACTIVE`인 `USER`와 `ADMIN` 모두 허용한다. `INACTIVE`는 역할에 관계없이 403으로 거절하고 새 플레이를 저장하지 않는다. 사용자가 “관리자도 게임 가능, 비활성 계정은 차단” 선택지를 확인했다.
- 기존 시연용 사용자 문맥을 재사용한다. `X-User-ID`와 `X-User-Role`은 DB와 대조하고, 멤버십은 게임 시작 자격을 제한하지 않으므로 선택 입력이다. 전달한 멤버십은 기존 공통 처리대로 DB와 대조한다. 사용자 헤더 확인을 제거하거나 신원 인증을 새로 구현하는 변경이 아니다.
- 이 선택의 구현 대상은 GD-156 색깔 게임 시작이다. 다른 업무 API의 관리자 권한이나 게임 결과·보상 계약을 일괄 변경하지 않는다.

GD-156의 시작 오류는 아래처럼 구현한다. GD-159의 플레이 부재·소유권·토큰 오류 번호는 이 표로 확정하지 않는다.

| 상황 | HTTP / 코드 | 처리 |
| --- | --- | --- |
| 비활성 사용자·관리자 | 403 / `GAME-001` | 시작하지 않음 |
| 게임 ID 조회 부재 | 404 / `GAME-002` | 시작하지 않음 |
| 비활성 게임 또는 미지원 게임·규칙 버전 | 409 / `GAME-003` | 시작하지 않음 |
| 지원 버전의 저장 규칙 오류 또는 DB 장애 | 공통 500 | 성공·플레이 시작으로 안내하지 않음. 내부 설정과 예외 원문을 공개하지 않음 |

공통 헤더·UUID 오류는 [공통 계약](common.md)과 기존 사용자 문맥의 오류 응답을 따른다. 프론트는 위 실패 응답을 받으면 게임을 시작하지 않고 안내한다. 토큰 수명·요청 빈도 등 미확정 운영 한도는 마지막 절의 후속 확인 사항으로 유지하며 임의 제한값을 추가하지 않는다.

201 성공 응답의 `data` 예시:

```json
{
  "playId": "0199f000-0000-7000-8000-000000000101",
  "playToken": "example-opaque-token",
  "ruleVersion": "color-word-v1",
  "startedAt": "2026-10-12T02:00:00Z",
  "rules": {
    "initialLives": 3,
    "pointsPerCorrect": 10,
    "initialTimeLimitMs": 3000,
    "timeLimitDecreaseMs": 80,
    "minimumTimeLimitMs": 1200
  },
  "gameData": {
    "generatorVersion": "color-word-generator-v1",
    "seed": 123456789
  }
}
```

- `playToken`은 서버가 발급한 해당 플레이에만 사용하는 값이다. 서버에서 사용자·게임·playId와 연결해 검증하며 사용자 인증을 대신하지 않는다.
- `seed`는 같은 문제 순서를 재현하기 위한 공개 시작값이다. 비밀값이나 부정 방지 증거가 아니다. 클라이언트가 제출한 seed나 정답표로 서버의 저장값을 교체하지 않는다.
- 시작 응답을 잃은 경우 자동으로 새 플레이를 계속 발급하지 않는다. 시작 실패를 표시하고 사용자의 다시 시작으로 새 플레이를 발급한다. 남겨진 미완료 플레이에는 점수·보상을 반영하지 않는다. 시작 요청 자체의 멱등 계약은 제공하지 않는다.

### 문제 생성 규약

Java와 TypeScript의 기본 난수 함수를 따로 사용하면 같은 seed여도 문제가 달라질 수 있다. 공유할 생성 알고리즘·색 순서·난수 소비 순서를 버전으로 고정한다.

- 난수: 0을 제외한 unsigned 32-bit seed로 시작하는 xorshift32. 각 호출에서 `x ^= x << 13`, `x ^= x >>> 17`, `x ^= x << 5`를 32비트 연산으로 수행하고, 결과를 unsigned 값으로 해석해 `2^32`로 나눈 값을 사용한다. 이는 재현용이며 암호학적 난수가 아니다.
- 색 순서는 현재 FE와 같은 `red`, `blue`, `yellow`, `green`이다.
- 단어를 먼저 추출하고 현재 FE의 0.75 불일치 분기, 다른 세 색 추출 순서, 직전 문제와 동일할 때 최대 10회 재추출 및 최종 대체 규칙을 동일하게 적용한다. 최초 플레이 규칙 확인과 별개로 이번 제안 방식 채택에 포함한다.
- 첫 문제의 이전 문제는 없다. 이전 플레이의 마지막 문제, 화면 미리보기, React 렌더링 횟수·재실행으로 난수를 소비하지 않는다. 실제 다음 문제로 넘어갈 때만 생성한다.
- 같은 seed의 문제 목록을 Java/TypeScript에서 비교하는 공통 예제와 테스트를 구현 시 고정한다. 일치 여부를 검증하기 전에는 생성기 구현·연동 완료로 표시하지 않는다.

## 3. 종료 — G04

`PUT /api/v1/games/{gameId}/plays/{playId}/result`

목숨을 모두 잃었을 때 제출한다. 최종 점수·남은 목숨·정답 여부·문제의 정답색을 신뢰값으로 보내지 않는다.

```json
{
  "playToken": "example-opaque-token",
  "validationData": {
    "answers": [
      { "sequence": 1, "answer": "red", "elapsedMs": 640 },
      { "sequence": 2, "answer": null, "elapsedMs": 2920 },
      { "sequence": 3, "answer": "red", "elapsedMs": 850 },
      { "sequence": 4, "answer": null, "elapsedMs": 2920 }
    ]
  }
}
```

위 seed와 생성 알고리즘으로 계산한 첫 네 문제의 `(word, ink)`는 `(yellow, red)`, `(green, yellow)`, `(yellow, yellow)`, `(green, green)`이다. 예제는 1번 정답, 2번 시간 초과, 3번 오답, 4번 시간 초과로 10점에 종료된다. JavaScript로 알고리즘의 예제 정합성만 확인했으며 Java/실제 프론트의 교차 검증은 아직 하지 않았다.

| 필드 | 의미 |
| --- | --- |
| `sequence` | 1부터 연속된 문제 번호. 오답·시간 초과 문제도 포함 |
| `answer` | 고른 색. `null`은 시간 초과. 속성 생략과 null은 구분 |
| `elapsedMs` | 해당 문제가 표시된 뒤 답변/시간 초과까지 실제 플레이 중인 구간만 합한 밀리초 정수 |

### 시간과 일시정지

- 기존 FE의 일시정지·탭 이동 시 자동 정지를 유지한다. 중지 시간, 시작/재개 카운트다운, 답변 뒤 정답 연출 시간은 문제의 `elapsedMs`에서 제외한다.
- 일시정지 후 같은 문제의 남은 시간을 이어서 사용한다. 해당 문제의 elapsedMs와 제한 시간을 초기화하지 않는다.
- 프론트는 단조 증가 시계로 활성 구간을 누적한다. 시스템 시계 변경으로 시간을 계산하지 않는다. 정수 밀리초 변환은 내림으로 통일한다.
- 정답/오답 클릭은 `0 <= elapsedMs < 해당 문제 제한 시간`에만 인정하고, 경계 이상이면 시간 초과 한 번으로 기록한다.
- 시간 초과는 `answer=null`, `elapsedMs=해당 제한 시간`으로 정규화한다. 애니메이션 완료 콜백이 늦게 실행됐다고 초과 시간을 그대로 기록하지 않는다. 클릭과 시간 초과가 경합해도 한 문제당 한 기록만 남긴다.
- 현재 FE의 `judge`는 답변색만 비교하므로 이 경계 처리와 시간 누적은 프론트 수정 대상이다.
- 서버가 볼 수 있는 총 경과 시간보다 활성 시간 합계가 클 때의 오차·허용 기준은 후속 계약이다. 네트워크 지연을 곧바로 부정으로 간주하지 않는다.

## 4. 서버 판정

1. 공통 사용자 문맥과 플레이의 소유자·게임·토큰을 확인한다.
2. 같은 playId의 기존 확정 결과를 먼저 확인한다. 동일 내용 재시도는 최초 결과를 반환한다.
3. 새로운 결과라면 서버가 저장한 seed·생성 버전·규칙으로 문제를 생성한다.
4. 답변을 1번부터 처리한다. 각 문제 시작 시점의 누적 정답 수로 제한 시간을 계산한다. 정답은 점수를 올리고, 오답·시간 초과는 목숨을 줄인다.
5. 세 번째 실패가 배열 마지막이어야 자연 종료다. 목숨이 남은 제출이나 이미 종료한 뒤의 추가 입력은 인정하지 않는다.
6. 정상 기록은 VALID로 확정하고 통계와 보상 자격을 처리한다. 오답/시간 초과가 있어도 정상 게임이다. 세 문제 모두 틀린 0점 플레이도 정상 기록이면 VALID다. 응모권은 한 판의 서버 판정 점수가 50점 이상일 때만 일일 지급 자격을 인정한다. 50점 미만은 통계만 반영하고 보상 청구·지급은 하지 않는다.

`INVALID`는 게임에 졌다는 뜻이 아니다. 서버가 확인한 규칙 위반 기록에만 사용하며 통계·보상에 반영하지 않는다. 서버/DB/지급 장애를 INVALID로 저장하지 않고 실패 후 재시도할 수 있게 한다.

## 5. 결과 응답과 보상

200 응답의 `data` 예시(위 답변 기록의 10점은 유효하지만 보상 기준 미만):

```json
{
  "playId": "0199f000-0000-7000-8000-000000000101",
  "status": "VALID",
  "score": 10,
  "completedAt": "2026-10-12T02:00:20Z",
  "reward": null
}
```

50점 이상인 별도의 정상 완료에서 당일 최초로 지급받았을 때의 `reward` 형식 예시:

```json
{
  "ticketCount": 1,
  "grade": "BRONZE",
  "grantedAt": "2026-10-12T02:00:20Z",
  "expiresAt": "2026-10-31T15:00:00Z"
}
```

- 색깔 게임의 reward 필드는 위 형식을 사용하고 실제 지급·만료 시각은 응모권 서비스가 반환한 값을 사용한다. 예제는 현재 TicketExpiry의 10월 지급분 만료인 11월 1일 00:00 KST를 UTC로 표현했다. 게임에서 만료 시각을 재계산하지 않는다. 출석 등 다른 도메인의 RewardReceipt DTO를 변경하는 계약이 아니다.
- 50점 미만이면 `reward=null`이며 일일 보상 기회를 소진하지 않는다. 여러 판의 누적 점수는 보상 판정에 사용하지 않는다. 다른 플레이로 오늘 보상을 이미 받았다면 `reward=null`이며 정상 점수·횟수는 계속 반영한다. INVALID는 `score=null`, `reward=null`이다.
- 같은 playId 재시도에는 최초 보상 내역까지 그대로 반환한다. 화면은 이를 새 보상으로 다시 합산하지 않고 보유량과 G05 통계를 재조회한다.
- 완료 시각은 서버 판정 시각이며 프론트가 보낸 종료 시각으로 대체하지 않는다.
- 색깔 게임의 KST 보상일은 서버에서 최초 유효 결과를 확정한 `completedAt`을 기준으로 한다. 시작일이나 클라이언트 종료 시각을 사용하지 않는다. 결과·청구·지급을 확정하는 트랜잭션이 롤백되면 완료된 것으로 간주하지 않는다. 성공 이후 재시도에서는 저장된 보상일·결과를 유지한다.
- 청구 생성·점수/통계 확정·기존 지급 서비스 호출의 성공/실패를 일관되게 처리한다. 응모권 등급과 만료를 게임에서 별도로 계산하지 않는다.

## 6. 재시도·오류·중도 종료

| 상황 | 처리 |
| --- | --- |
| 같은 playId·같은 입력 재제출 | 최초 확정 결과 200, 중복 점수·보상 없음 |
| 동일 플레이 처리 중 | 202 PROCESSING, score/completedAt/reward는 null, 같은 본문으로 재시도 |
| 같은 playId·변경된 입력 | 409 충돌. 기존 확정 결과는 변경하지 않음 |
| JSON/필수 필드/enum/숫자 형식 오류 | 공통 400, 정상적인 오답과 구분 |
| 타인 플레이·다른 게임·잘못된 토큰 | 소유권을 우선 검증하고 오류 반환. 정보 은닉 기준과 최종 번호는 공통 계약과 조율 |
| 확인된 플레이 기록 규칙 위반 | INVALID 확정, 추가 점수·보상 없음 |
| 요청 빈도 제한 | 공통 계약에 맞춘 429·Retry-After, 제한 수치는 담당자와 조율 |
| 서버/DB/지급 실패 | 5xx, 확정되지 않은 결과는 동일 플레이·본문으로 재시도 |
| 중간에 나가기·창 닫기 | 미완료 플레이로 두고 점수·보상을 반영하지 않음. 자연 종료 후 제출 실패의 재시도는 구분 |

동일 입력은 JSON 키 순서나 공백이 아닌 정규화된 값으로 비교한다. 배열 순서와 각 문제의 번호·색·시간은 비교 대상이다. 이미 확정된 정상 요청은 현재 게임 정책·날짜 변경으로 새 결과를 만들지 않는다. 초기 운영의 토큰 수명·재조회 보존은 아래 2026-10-15 선택을 따른다.

### G04 오류 은닉·요청 한도·지급 연결 — 2026-10-15 사용자 선택

- 변경 전: 플레이 부재·소유권·토큰 오류의 공개 번호와 요청·기록·만료·보존 한도는 구현 전 확인 항목이었다.
- 변경 후: 사용자가 추천안을 각각 선택했다. 없는 플레이, 다른 사용자 플레이, 경로 게임 불일치, 잘못된 토큰은 모두 404 `GAME-005`로 반환하며 존재 여부나 실패 세부 사유를 구분하지 않는다.
- 같은 플레이의 확정된 입력 변경은 409 `GAME-006`이다. G04는 기존 권한 U를 유지해 활성 일반 사용자만 제출하며 비활성 사용자·ADMIN은 403 `GAME-007`이다. G03의 관리자 시작 허용을 결과·보상 자격까지 확대하지 않는다.
- 초기 G04 요청 본문은 최대 1MiB(1,048,576바이트), `validationData.answers`는 최대 10,000개다. 둘 중 하나라도 초과하면 413 `GAME-008`로 거절하며 결과·통계·청구·지급을 저장하지 않는다. 빈 배열·순서·시간 규칙은 별도 서버 판정 대상이며 단순 크기 초과를 INVALID 결과로 확정하지 않는다.
- 토큰의 시간 만료와 완료 결과 자동 삭제는 초기 운영에 도입하지 않는다. 정상적인 긴 플레이·일시정지와 완료 요청 재시도를 임의 기간으로 차단하지 않는다. 추후 도입 시 기존 재시도·보상 근거 보존 및 FE 영향을 확인해 별도 결정한다.
- 결과·유효 통계·일일 보상 청구와 기존 `TicketGrantService` 지급 호출을 같은 업무 트랜잭션으로 확정한다. 응모권 담당 서비스 내부의 등급·만료·원본 청구 검증 정책은 변경하지 않는다. 지급 실패는 INVALID로 치환하지 않고 전체 롤백 후 같은 요청으로 재시도한다.
- 실제 동일 플레이 처리가 진행 중인 경우만 202 `PROCESSING`을 제공한다. 소유권·토큰을 확인하기 전에 잠금 경합 여부를 노출하지 않는다. 재요청은 같은 플레이·원본 입력을 유지한다.
- 구현·테스트·실제 FE 연결 완료는 이 계약 선택과 별도로 검증한다. 지급 전 차단·빈도 제한의 담당자 연동은 기존 후속 범위를 유지하며 임의 탐지 임계값을 추가하지 않는다.

프론트는 종료 기록과 playId를 재시도 동안 유지한다. 새 판 시작으로 이전 요청의 기록을 덮어쓰지 않고, 늦게 온 이전 판 응답을 새 판 점수·보상으로 표시하지 않는다. 새로고침 후 재시도를 지원할 저장 위치·보존 기간은 프론트와 확인한다.

## 7. 이 방식의 범위와 구현 후속

서버는 자기 문제 생성 기준으로 제출 기록의 정합성과 점수를 계산할 수 있다. 그러나 공개 seed로 향후 정답을 계산하거나 답변·활성 시간을 조작할 수 있으므로 **기록만으로 실제 사람의 플레이나 실제 반응 시간을 증명하지 못한다**. playToken 역시 클라이언트 기록의 진실성을 증명하지 않는다.

이 한계를 명시한 일괄 제출 방식을 이번 구현 기준으로 채택했다. 강한 실시간 부정 방지를 보장하지 않는다. 종수와 차단 기준·근거 기록을 연결하며, 향후 온라인 문제 발급/검증이 필요하면 별도 계약 변경으로 다룬다. 의심만으로 보상을 보류하는 정책을 임의 추가하지 않는다.

구현 전 확인할 항목:

- 채택된 생성 버전의 공통 테스트 벡터와 실제 Java/TypeScript 구현 일치 검증.
- 요청 크기·기록 수와 초기 만료·보존 정책은 위 2026-10-15 선택을 따른다. 운영 한도 변경이나 분할 전송 도입 시 정상 플레이·재시도·보상 조건의 영향을 별도로 확인한다.
- 채택된 게임 RewardReceipt와 응모권 담당의 실제 반환값 매핑 검증.
- G04 공개 오류·소유권 은닉은 위 2026-10-15 선택을 따른다. 차단 기록의 타 담당 연동, 공개 DTO 적용 위치와 프론트 변경 내용을 공유하고 실제 반영 여부를 확인한다.

## 8. 확인할 테스트

- Java/TypeScript 같은 seed의 문제열 일치. 첫 문제·새 판·일시정지·렌더링 횟수에 영향 없음.
- 정답/오답/시간 초과, 제한 시간 직전·정확히 경계, 최소 제한 시간, 세 번째 실패 뒤 추가 입력.
- 일시정지·자동 정지·재개 카운트다운·정답 연출 시간 제외, 한 문제의 중복 입력 방지.
- 0점·40점 정상 종료는 VALID 및 통계 반영·보상 없음, 50점 정상 종료의 당일 최초 지급, 저득점 이후 같은 날 기준 충족 시 지급, 낮은 점수 여러 판의 합산으로 지급하지 않음.
- 타인 플레이, 변경 본문, 이미 확정한 결과의 자정 이후 재시도.
- 같은 날 다른 플레이 보상 경합, 저장/지급 실패 롤백, 최초 등급·지급 시각 보존.
