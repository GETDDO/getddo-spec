# ADR-022: 자동 추첨과 관리자 수동 최초 공개

- 상태: 제안
- 작성자 / 날짜: Codex / 2026-10-14
- 검토자: 사용자 정책 확정 — ADR 문서 담당자 확인 전
- 관련 작업: GD-86·GD-140·GD-199 / [작업 기록](../04-worklogs/2026-10-14-drawing-followup-scope.md)
- 대체 범위: ADR-009의 자동 최초 발표·카운트다운. 2026-10-15 보완은 이 ADR의 2026-10-14 확인/공개 별도 요청 해석을 대체한다. 마감 +5분 자동 추첨·기존 개별 취소·재추첨·이력 보존은 유지한다.

## 배경

사용자는 이벤트 마감 시간대에 관리자가 명단을 확인할 수 있으며, 발표 전 개별 당첨 취소·빈 자리 재추첨을 사용자에게 노출하지 않고 처리한 뒤 수동 공개하도록 요청했다. 추첨 자체는 자동으로 유지하고 응모자 후보 제외를 추가하지 않는다고 확인했다.

## 결정과 이유

- 자동 추첨 → 관리자 육안 검토 → 필요 시 개별 당첨 취소·빈 자리 재추첨 → 발표 요청 한 번으로 최종 확인 기록 저장·전체 명단 공개 → 프론트엔드 발표를 사용한다.
- 자동 추첨 결과 확정·재추첨 완료·마감 후 시간 경과만으로 공개하지 않는다. 관리자는 명단을 육안으로 검토하며 별도 확인 완료 버튼이나 사전 확인 API 호출을 요구하지 않는다. 발표 버튼의 요청 한 번으로 필요한 실행별 최종 확인 기록과 공개 명단·기존 알림 작업을 같은 트랜잭션에 저장한다. 스케줄러는 자동 추첨까지만 처리하며 자동 최초 공개·공개 재호출을 수행하지 않는다.
- 사용자 화면은 공개 전 '응모 마감 · 결과 발표 대기'다. 고정된 공개 예정 시각과 5분 카운트다운은 제공하지 않는다.
- 최초 확인·수동 공개 연결은 GD-199에서 보완한다. 주요 정책은 [요구사항](../00-requirements/functional-requirements.md#10-결과-발표)과 [추첨 규칙](../02-domain/drawing.md#결과-발표)을 원본으로 한다.

## 검토한 대안

기존 마감 +5분 자동 발표와 관리자 검토 후 수동 발표를 대화에서 비교했다. 사용자는 담당자가 확인할 수 있는 운영 시간대를 이유로 수동 발표를 선택했다. 성능·운영 실험은 수행하지 않았다.

## 영향과 재검토 조건

- 프론트엔드는 카운트다운을 발표 대기로 바꾸고 실제 공개 결과만 연출한다. E08/E09의 publicationScheduledAt은 제외하며 실제 publishedAt과 서버 시각은 유지한다.
- `POST /api/v1/admin/draws/{runId}/result-confirmation`을 정상 최초 INITIAL 결과까지 확장해 발표 요청 한 번으로 최종 확인·공개한다. 최초 공개 전 취소·재추첨이 있으면 유지 당첨자와 최종 재추첨 결과를 합친 전체 명단을 처리하며 실행 하나의 명단만 부분 공개하지 않는다. 기존 `POST /api/v1/admin/draws/{runId}/publication`은 최초 공개 후 재추첨 명단 갱신 용도로 유지하고 최초 발표 전에 연달아 호출하지 않는다. 명단 동일성 입력·DTO·업무 오류의 PR 대조 상세와 병합 후 적용 상태는 [추첨 API](../05-api/drawing.md#gd-199-pr-대조-계약--병합-후-적용-예정)를 따른다.
- 명단 변경 뒤 이전 확인으로 새 명단을 공개하지 않으며, 취소 이벤트·미확정/미확인 결과·일부 명단 공개를 차단한다. 공개 요청의 중복 방지·기존 이력 보존은 유지한다.
- 기존 관리자 취소·재추첨 API의 삭제·발표 후 호출 금지는 이번 결정이 아니다. 발표 후 취소·재추첨을 운영에서 사용하지 않는 전제로 사용자 중간 표시는 GD-140 범위에서 제외한다.
- 실제 공개에 연결된 알림 등록·발송·전달 재시도는 유지한다. 알림 담당 문서의 자동 발표 문구는 담당자 동기화 대상으로 남기며 이번 작업에서 알림 구현·알림 문서 두 파일을 수정하지 않는다.
- 정책 반영과 코드·배포 완료를 구분한다. 기존 Flyway·과거 공개 기록을 삭제하거나 소급 변경하지 않는다.

## 2026-10-15 결정 보완 이력

- 당시 결정: 2026-10-14에는 관리자 확인 저장과 공개를 별도 동작으로 문서화했다.
- 변경 이유: 사용자는 확인을 명단의 육안 검토라는 의미로 설명했으며 별도 확인 버튼을 요청하지 않았다. 발표 버튼 한 번으로 최종 확인·공개하는 기존 서비스 흐름을 재사용하기로 했다.
- 현재 결정: `POST /api/v1/admin/draws/{runId}/result-confirmation`을 정상 최초 INITIAL 결과까지 확장해 발표 요청 한 번으로 최종 확인·공개한다. 최초 공개 전 취소·재추첨이 있으면 유지 당첨자와 최종 재추첨 결과를 합친 전체 명단을 처리하며 실행 하나의 명단만 부분 공개하지 않는다. 기존 `POST /api/v1/admin/draws/{runId}/publication`은 최초 공개 후 재추첨 명단 갱신 용도로 유지하고 최초 발표 전에 연달아 호출하지 않는다.
- 검토 중 명단이 변경되면 이전 화면의 발표 요청을 거절하고 최신 명단을 다시 확인하도록 안내한다. 동일 발표 요청 재시도는 기존 성공 결과를 반환하며 공개 버전·알림을 중복 생성하지 않는다. 명단 변경 요청과 동일 처리 재시도를 구분한다. 활성 관리자라면 발표할 수 있고 실제 발표자·시각을 기록한다.
- ADR 상태는 제안이며 사용자 동작 선택과 담당자 문서 검토를 구분한다. 기존 공개/확인 기록·Flyway를 삭제하거나 소급 변경하지 않는다.
