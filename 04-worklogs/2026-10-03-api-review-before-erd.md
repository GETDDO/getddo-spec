# 작업 기록: ERD 수정 전 API 명세 다각도 검토

- 작성일: 2026-10-03
- 관련 이슈 / PR: 없음
- 상태: 검토 대기
- 영향 범위: 공통 / 프론트엔드 / 백엔드
- 검토 기준 커밋: `25181001b9642ce3b83946a09359dc49219b8ea4`

## 목적

요구사항과 API를 먼저 검토한 뒤 DB와 ERD를 수정하려는 작업 순서에 맞춰, 현재 API 계약에서 보완할 내용과 담당자 결정이 필요한 내용을 정리한다.

검토 결과, 주요 기능의 API 목록은 갖춰져 있지만 상태 전이, 관리자 업무의 연결 순서, 일부 입력·응답 구조가 아직 미완성이다. 현재 초안을 그대로 최종 계약이나 ERD의 확정 근거로 삼기보다 아래 우선 항목을 먼저 정리하는 것을 권고한다. 이 문서의 권고는 정책 채택이나 구현 결함의 실증을 의미하지 않는다.

## 한 일

- 변경 전 로컬 작업 트리가 깨끗하고 로컬 HEAD와 원격 main이 같은 커밋임을 확인했다.
- [요구사항](../00-requirements/functional-requirements.md), [구현 범위](../00-requirements/scope.md), [도메인 규칙](../02-domain/README.md), 관련 ADR과 [API 계약](../05-api/README.md)을 대조했다.
- 요구사항 충족, 프론트엔드 연동·권한, 정합성·향후 ERD 영향의 세 관점을 독립 검토하고 지적의 근거와 중복을 재확인했다.
- API 표를 집계해 12개 도메인 파일의 API ID 80개와 ID 중복 없음을 확인했다.
- 확정 규칙과의 충돌, 이미 알려진 후속 계약, 이번 검토에서 구체화한 계약 공백을 구분했다.
- 요구사항·API 본문·DB·ERD는 변경하지 않았다. 실행 서버나 동시성 구현을 테스트한 결과가 아니라 문서 계약 검토다.

## 확인된 내용

### 확정 범위와 유지할 설계

[API 계약의 상태](../05-api/README.md)에 따르면 사용자 알림 N01~N03만 확정이고 나머지 77개는 검토 대기다. 2026-10-01 회의 메모는 기존 기준 문서에 반영되지 않은 기록이므로 확정 요구사항으로 사용하지 않았다.

### API와 ERD 확정 전에 우선 정리할 항목

아래 P1은 관련 API·데이터 관계를 확정하기 전에 해결할 항목이며, 실제 서비스 장애나 취약점의 심각도 등급이 아니다.

#### R01 P1 제외 반환과 부정 지급 회수의 호출 순서

- 분류: 기존 원칙을 실행할 API 연결 계약의 공백.
- 근거: [AR03과 AR05](../05-api/abuse.md#검토와-참여-제외)는 별도 호출이고, AR03은 부정 지급분의 반환을 이미 확정된 회수 결정과 연결한다. [응모권 규칙](../02-domain/ticket.md#부정-획득-응모권-회수)은 제외로 반환되는 부정 획득분을 반환·회수 같은 트랜잭션으로 처리하도록 정한다.
- 재현할 계약 시나리오: 부정 지급분으로 응모한 사용자를 회수 대상 결정 전에 제외하거나, 이벤트 취소 반환과 제외가 동시에 요청된다. 현재 문서에는 선행 결정이 없는 경우의 거절·연결 방식이 없어 반환된 부정 지급분의 중간 재사용을 어떻게 막는지 알 수 없다.
- 권고: 검토 확정 → 회수 대상 결정 → 제외·반환·회수의 허용 순서와 선행 조건 미충족 응답을 명시한다. 순서는 제안이며, 하나의 업무 요청으로 연결하는 대안도 검토할 수 있다. `ALLOW + excludeFromEvent=true` 같은 상충 입력의 허용 여부도 정한다.
- ERD 영향: 검토 결정, 원본 지급, 차감 출처, 반환 및 실제 회수 사이의 추적 관계와 중복 처리 단위가 달라진다.

#### R02 P1 최초 발표 전 재추첨과 발표 후 취소의 조회 상태

- 분류: API 초안이 이미 담당자 계약으로 남긴 상태 처리의 구체화.
- 근거: [AD05·AD06과 공개 결과](../05-api/drawing.md)는 최초 발표 전 당첨 취소·재추첨을 다루지만 AD06은 최초 발표 이후에만 허용한다. [이벤트 취소](../05-api/event.md#상태-운영)는 발표 이후에도 가능하다.
- 재현할 계약 시나리오: 마감 4분 후 당첨을 취소하고 재추첨한 상태에서 5분 자동 발표 시각이 된다. 새 결과의 확인 방법과 자동 발표에 쓸 결과가 정해져 있지 않다. 발표 후 이벤트를 취소한 경우에도 E08의 `isPublished/revision/prizes`, E09의 당첨·취소 표시 조합이 정해져 있지 않다.
- 권고: 최초 발표 전·후, 재추첨 준비·확정·관리자 확인, 이벤트 취소별 E01/E02/E08/E09 응답표를 작성한다. 최초 발표 전 재추첨의 확인 절차를 정하되 정상 최초 발표에 관리자 승인 대기를 추가하지 않는다.
- ERD 영향: 추첨 확정 결과, 현재 공개 명단, 당첨 취소와 이벤트 취소를 구별하고 변경 이력을 보존해야 한다.

#### R03 P1 서로 다른 재추첨과 관리자 결정의 동시 요청

- 분류: 중복 방지 원칙은 있으나 외부에 보이는 충돌 처리 계약이 부족함.
- 근거: [AD05](../05-api/drawing.md#당첨-취소와-즉시-재추첨)는 당첨 한 건을 대상으로 하며, [AD06](../05-api/drawing.md#공개-명단-반영)은 같은 실행의 재반영을 막는다. [AR03·AR05](../05-api/abuse.md)는 판단 변경·회수 대상 대체를 지원하는 형태다.
- 재현할 계약 시나리오: 같은 이벤트의 서로 다른 당첨 두 건을 동시에 취소하거나 두 관리자가 서로 다른 실행을 공개 반영한다. 같은 검토 건의 ALLOW와 CONFIRM 또는 같은 회수 대상의 대체 요청도 경합할 수 있다.
- 권고: 이벤트·검토별 선행 처리와 충돌 응답을 정한다. 진행 중 새 요청을 대기시킬지 거절할지, 이전 revision·결정을 기준으로 한 요청을 어떻게 처리할지 명시한다. 이벤트 취소가 확정된 뒤 새 공개 명단이나 변경 알림이 생성되지 않는 조건도 확인한다. 특정 잠금 방식은 공용 API 문서에서 정하지 않는다.
- ERD 영향: 당첨 취소와 재추첨 실행의 연결, 경품 자리별 현재 유효 당첨, 공개 revision, 검토 결정과 그 효과의 이력 관계를 점검해야 한다.

#### R04 P1 미션의 완료 조건과 공개 흐름

- 분류: 초안에 명시된 미완료 계약.
- 근거: [미션 API](../05-api/mission.md#미션문항)는 다문항 완료·채점, OX 표현, 단답 정규화를 후속 계약으로 둔다. AM03은 생성만 제공하고 `DRAFT/ACTIVE/ENDED`의 전이·노출은 미정이다.
- 재현할 계약 시나리오: 퀴즈 3문항 중 2문항만 맞혔거나 OX 문항에 선택지를 몇 개 등록할지 정해야 한다. 미래 시작 시각으로 등록한 DRAFT 미션이 자동 공개되는지도 프론트엔드가 판단할 수 없다.
- 권고: 지원할 문항 유형과 유형별 필수 필드, 정답 수, 다문항 달성 조건부터 좁혀 확정한다. 등록 후 시간에 따라 자동 노출할지 별도 공개 동작이 필요한지 정한 뒤 필요한 API만 보완한다. 초안 수정·삭제를 반드시 신규 요구사항으로 추가할 필요는 없다.
- ERD 영향: 문항·선택지·답변·제출 시도와 사용자별 최종 달성의 관계, 공개 상태의 의미가 달라진다.

#### R05 P1 게임별 입력 구조와 보상 기준일

- 분류: [기존 게임 담당자 후속 작업](../00-requirements/pending-decisions.md#게임)의 구체화.
- 근거: [게임 API](../05-api/game.md)는 `rules:object`, `validationData:object`, 자정을 걸친 플레이의 보상일, 운영·보상 조건 변경을 후속 계약으로 남겼다. 문서 자체도 G02~G04·AG03이 최종 계약이 아니라고 명시한다.
- 재현할 계약 시나리오: 23:59 시작, 00:01 제출, 00:02 판정한 플레이의 보상일과 적용 규칙 버전을 선택해야 한다. 관리자가 다음 날부터 적용할 보상 조건을 바꿀 요청도 없다.
- 권고: 게임 종류별 요청·응답 예시와 검증 데이터 구조, 보상 기준일의 기준 순간, 규칙 버전 및 허용된 운영 변경 계약을 정한다. 기존 하루 1회 1장 정책은 유지한다.
- ERD 영향: 플레이와 규칙 버전, 보상 업무일, 정책 적용 이력의 연결을 먼저 정해야 한다.

#### R06 P1 이미지 파일에서 imageKey를 얻는 경로

- 분류: 공통 계약이 후속 작업으로 남긴 프론트엔드 연동 공백.
- 근거: [공통 이미지 계약](../05-api/common.md#경로권한입출력)은 쓰기에 `imageKey`를 사용하고 업로드 방식을 위임한다. [AB02](../05-api/banner.md#관리자-배너-관리)는 `imageKey`를 필수로 요구한다.
- 재현할 계약 시나리오: 관리자 화면에서 배너 파일을 선택했지만 저장 요청에 사용할 키를 얻는 요청·응답이 없다.
- 권고: 업로드 방식, 업로드 결과의 키, 연결 가능한 키의 검증과 실패 응답을 연결된 계약으로 제공한다. 이미 다른 저장소에 업로드 계약이 있다면 복제하지 말고 기준 문서를 연결한다. 형식·용량 수치는 [기존 담당자 결정](../00-requirements/pending-decisions.md#배너)을 따른다.
- ERD 영향: 여러 도메인이 이미지 자산을 공유하는지와 저장할 참조의 의미를 확인하되, 파일 저장소 내부 설계는 백엔드에서 정한다.

| R11 처리 중 요청과 거절 사유 | 응모·미션은 완료된 동일 요청의 응답은 있지만 처리 중 중복 응답은 미명시다. 게임 202 이후 재조회 간격도 없다. E07 reasons는 string 배열만 명시한다. | [공통 중복 요청](../05-api/common.md#중복-요청), [G04](../05-api/game.md), [E07](../05-api/entry.md)에 처리 중 응답·재시도 조건과 안정적인 사유 코드를 명시한다. |
| R12 운영 정책의 예약 재수정 | AP02/AP04는 같은 적용일·월에 두 번째 생성 시 409이며 예약 정책 재수정 방식은 미정이다. | [출석 정책 API](../05-api/attendance.md#관리자-출석-정책)에 적용 전 예약을 수정·대체·취소할 수 있는지 정한다. 현재 정책과 과거 달성 기록의 소급 변경은 금지된 채로 유지한다. |
| R13 결과와 원본 ID의 의미 | 재추첨 DrawRunDetail.results가 바뀐 자리만인지 전체 배정인지 불명확하다. 회수 요청의 originalGrantId와 지급 조회의 ledgerId도 연결을 명시할 필요가 있다. | [추첨 DTO](../05-api/drawing.md#실행스냅샷검증), [회수 DTO](../05-api/abuse.md#부정-획득-원본-지급분-회수), [지급 조회](../05-api/ticket.md#관리자-응모권-조회)의 ID·결과 범위를 정의한다. |
| R14 게임 최초 결과와 사후 무효화 | G04는 최초 확정 결과를 재사용하고 AR07은 점수를 무효화한다. 사후 재조회 의미는 초안에서도 보류다. | [G04](../05-api/game.md)와 [AR07](../05-api/abuse.md#부정-게임-점수-무효화)에서 원판정·현재 효력의 응답 의미를 정한다. 보상 영수증 반환을 새 지급으로 해석하지 않는다. |

출석은 [공통 계약](../05-api/common.md#중복-요청)에 자정 이후 요청을 새 업무일로 처리한다고 명시돼 있다. 따라서 자정 재시도를 정책 위반으로 단정하지 않았다. 다만 응답 유실 뒤 자정을 넘긴 자동 재시도는 다음 날 출석이 될 수 있으므로 프론트엔드에서 기준일 재조회와 사용자 동작을 어떻게 연결할지 확인할 필요가 있다.

### 기존 미결정 사항과 문서 정리

발표 장애 시 복구·안내, 마스킹 세부 규칙, 이미지 형식·용량, 게임 종류·검증, INACTIVE 사용자와 시연용 사용자 목록은 [기존 미결정 목록](../00-requirements/pending-decisions.md)에 있는 내용이다. 새로 발견한 결함으로 세지 않았다. 월말 소진용 이벤트의 지정 조건과 삭제 이벤트 알림 처리는 [이벤트 API](../05-api/event.md)에 이미 담당자 계약으로 남아 있다.

API 본문의 이름만 있는 후속 계약은 실제 기준 문서로 연결해야 한다. 이번에는 정책을 선택하지 않고 [API 검토 후속 질문](../00-requirements/pending-decisions.md#api-검토-후속-질문)에 모았다.

[ADR-013](../03-decisions/013-linear-drawing-weight.md)은 상태가 제안인데 [추첨 도메인](../02-domain/drawing.md#가중치-및-중복-당첨)은 가중치 환산을 확정 규칙으로 기술한다. 저장소 우선순위에 따라 이번 검토는 도메인 규칙을 기준으로 했으며, ADR 상태 표시는 담당자에게 정리를 권고한다.
