# 작업 기록: 사용자 문맥 헤더 `X-User-Role` 충돌 정리와 결정

- 작성일: 2026-10-12
- 관련 이슈 / PR: 백엔드 GD-52 (`getddo-be` `dev`의 `CurrentUserArgumentResolver`, `docs/02-api/user-profile.md`)
- 상태: 완료 — 백엔드 구현 기준으로 공용 명세를 정렬했다. 프론트 호출 반영은 후속 작업
- 영향 범위: 공통 / 프론트엔드 / 백엔드

## 목적

공용 명세 안에서 사용자 문맥 헤더 정의가 서로 달랐다. 백엔드 구현과 확정 계약을 확인해 기준을 정하고, 공용 명세를 그 기준에 맞춘다.

## 확인된 사실

| 출처 | 내용 |
| --- | --- |
| 공통 계약 `common.md` (변경 전) | `X-User-Role`은 받지 않는다. 역할은 DB로만 판단 (권고안, 2026-09-28 답변 반영) |
| 관리자 알림 AN01~AN05 (2026-10-12 확정) | `X-User-ID`·`X-User-Role` 필수, DB 값과 대조 |
| 백엔드 `dev` 구현 (`CurrentUserArgumentResolver`) | `X-User-ID`·`X-User-Role` 필수. 역할 헤더는 **DB 역할과 대조만** 하고 권한 부여에 쓰지 않음. 불일치는 403 `USER-004` |
| 백엔드 `dev` 구현 (멤버십) | 기본 `@CurrentUser`에서 USER는 DB와 일치하는 `X-User-Membership` 필수. 알림 API는 선택 |
| 백엔드 `docs/02-api/user-profile.md` | 백엔드 스스로 "공용 명세의 초안과 차이가 있으니 프론트 호출과 공용 명세를 함께 맞춘다"고 기록. 공용 명세의 확정 상태는 백엔드 문서에서 바꾸지 않음 |
| 프론트엔드 `sessionSync.ts` | `X-User-ID`·`X-User-Membership`만 전송. `X-User-Role` 미전송 → 백엔드 연동 시 알림·U01·관리자 이벤트 등록이 거절됨 |

## 결정

**헤더는 역할을 입력받아 DB와 대조하고, 권한은 DB 역할로만 판단한다.**

백엔드는 이미 이 방식으로 구현되어 있다. 따라서 백엔드 변경 없이 공용 명세와 프론트엔드를 맞추면 된다. 백엔드에 별도 요청할 항목은 없다.

## 선택지 비교

| 안 | 내용 | 평가 |
| --- | --- | --- |
| A. 역할 헤더 제거 | 백엔드 리졸버가 역할을 DB에서만 읽음 | 헤더 신뢰 문제는 없으나 백엔드 구현 변경과 AN 문구 변경이 필요. 현재 구현과 반대 |
| **B'. 역할 헤더 필수 + DB 대조 (채택)** | 헤더는 일치 확인용, 권한은 DB | 백엔드 변경 없음. 클라이언트가 역할을 바꿔 보내도 권한은 상승하지 않음 (불일치는 거절) |
| C. 헤더를 권한 근거로 사용 | 헤더 값으로 권한 부여 | 임의 관리자 호출 가능. 비기능 요구("클라이언트 역할 값을 신뢰하지 않음")와 충돌 — 제외 |

## 반영 내용

- `05-api/common.md`: `X-User-Role` 행 추가, 멤버십 필수 조건 명시, "받지 않는다" 문장을 DB 대조 규칙으로 교체, 예제에 역할 헤더 추가
- `05-api/notification.md`: N01~N03 헤더 설명에 `X-User-Role` 필수 추가 (백엔드 구현과 일치, 확정 응답·오류 계약은 변경 없음)
- 프론트 문서 `getddo-fe/docs/CONTEXT.md`, `README.md`: 결정 내용 반영
